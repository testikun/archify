# Squad manager–worker coordination

Scope: the selected clean checkout of `https://github.com/mco-org/squad`, revision `8146bcc1c38c439aedaf3ff44548c830654c8621`. All evidence is local; no live services or external repository content were used. The diagram's source references retain repository-relative paths and inclusive line ranges. Role references describe the built-in defaults, not proof that an external client follows them.

## How the path works

1. An external manager and worker each invoke Squad from the same workspace. `find_workspace` walks upward to `.squad`; `open_store` opens `.squad/messages.db` (`src/main.rs:430–445`). `join` registers an active agent, writes its token and prints role text (`src/main.rs:610–640`). Workspace custom roles override the built-ins (`src/roles.rs:15–29`). An active name collision gets a numbered ID; archived identities can be reactivated (`src/store.rs:142–175`).
2. The manager calls `squad task create manager worker --title "..." --body "..."`. CLI checks its sender/session (`src/main.rs:973–981`). Store's transaction requires both creator and assignee to be active, inserts the `queued` task, and inserts an unread `task_assigned` message linked by `task_id`, then commits (`src/store.rs:452–546`). No manager-role check is present in that path.
3. Worker calls `squad receive worker [--wait]`. Store selects unread messages and marks those selected IDs read transactionally (`src/store.rs:340–374`). Text output enriches assignment messages by looking up the task (`src/main.rs:487–520`). Receiving does not change task status. Waiting is CLI polling every 500 ms, with a 30-second heartbeat, session replacement checks, and a per-agent exclusive file lock at **workspace-root** `locks/<id>.receive.lock`, not under `.squad` (`src/main.rs:786–869`).
4. Worker explicitly calls `task ack worker <task-id>`: active agent, queued task, and matching assignee are required. The conditional update records `acked`, `lease_owner`, and a 15-minute expiry (`src/store.rs:13`, `src/store.rs:624–650`). Work execution itself belongs to the external client, not Store. Worker calls `task complete worker <task-id> --summary "..."`: active agent, acked state and matching lease owner are required, but expiry is not tested. Completion stores the summary and timestamps; it does not insert a message (`src/store.rs:653–679`).
5. Manager reads `task list` to inspect persisted summaries (`src/main.rs:1017–1049`; `src/store.rs:563–621`), or worker separately sends a freeform message. `send` validates sender/session, supports direct metadata (`task_id`, `reply_to`) or broadcast to other active agents, and delegates message writes (`src/main.rs:706–746`; `src/store.rs:290–337`). `receive` returns messages through stdout; there is no manager-to-worker socket or broker in this slice.

## Boundaries and caveats

- The two CLI caller arrows mean invocations; stdout flows back to each caller. The CLI-to-Store arrow is an in-process Rust call/return, not an RPC. Persistence survives individual command processes: Store owns SQL access to the shared database. WAL and a 5-second busy timeout are configured at open (`src/store.rs:45–107`).
- Manager/worker responsibilities are prompt conventions (`src/roles/manager.md:1–22`, `src/roles/worker.md:1–15`), not enforced authorization or automatic AI scheduling. The source does not establish whether any particular external AI client obeys those instructions, stays running, or executes tasks successfully. The diagram therefore does not invent an LLM runtime or automatic manager loop.
- Session checks compare database/local file tokens and require active agents; missing local token files are accepted for compatibility (`src/main.rs:451–484`; `src/session.rs:50–59`). These are local displacement checks, not a security boundary between mutually untrusted clients. In a wait loop the token captured at entry is checked again on each poll.
- `task requeue` has no agent/session check in its CLI handler (`src/main.rs:1006–1014`). Store optionally checks a new assignee is active, resets state/lease/result with a conditional update, but generates no assignment message (`src/store.rs:681–718`). No expiry-triggered automatic requeue is evidenced in the traced path; a lease timestamp is not proof of a running recovery scheduler.
- Inspector/review prompts, team templates, setup/install flows and tmux launching are intentionally outside this overview. The diagram does not claim their absence from the repository.

## Simplification / ablation review

The overview deliberately merges command dispatch, workspace discovery, stdout formatting and wait polling into one CLI component, and all task/message SQL operations into Store. Splitting these into per-command services would imply unsupported deployment boundaries. Conversely, removing Store would hide who owns transactions and state gates; merging the database with the command process would hide cross-process persistence; merging manager and worker would hide assignment versus acknowledgment ownership. Those distinctions are retained. Session files and role prompts remain separate because they have different effects: displacement checks versus advisory behavior. Redundant return arrows and separate per-table nodes are omitted; labels and component explanations preserve their meaning.

An actual draft ablation removed the command-process boundary and checked that all connection endpoints still resolved. The topology remained intact, but the visible distinction between in-process CLI/Store calls and persisted workspace files was no longer explicit in the default READ view. That failed the requested important-boundaries criterion, so the boundary was restored byte-for-byte. This was a semantic ablation, not a benchmark or a separate browser test. The delivered candidate remains the one bound by the passing finalizer and browser receipts.
