# Hive task path: source evidence and scope

Repository identity: `https://github.com/tt-a1i/hive`, revision `f8f1343da6595a232f0baba7f0ea5b5a58fe0e9c`. The selected checkout was clean. References below are relative to `project/`; the diagram's focusable components retain source ranges. Links are deliberately local-only; no remote repository lookup was needed.

## How the task reaches the worker

1. **Browser input enters a real CLI terminal.** xterm's `onData` calls the terminal client's `sendInput` (`web/src/terminal/useTerminalRun.ts:640–647`). The client emits IO input and receives output (`web/src/terminal/terminal-client.ts:144–205`). The WebSocket server checks the UI session and live run before attaching `/ws/terminal/:runId/io` and `/control` (`src/server/terminal-ws-server.ts:87–130`). The hub calls `store.writeRunInput` (`src/server/terminal-stream-hub.ts:300–316`).
2. **The orchestrator explicitly delegates.** Its `team send <member> ...` posts to `http://127.0.0.1:${HIVE_PORT}/api/team/send`, with workspace, agent identity and token (`src/cli/team.ts:105`, `src/cli/team.ts:1255–1267`). Authentication verifies the token and workspace membership; role permissions allow orchestrators to send and workers to status/report (`src/server/team-authz.ts:27–98`). The route resolves the named member and returns HTTP 202 with a dispatch ID (`src/server/routes-team.ts:127–166`). Acceptance is not proof of execution or completion.
3. **The runtime owns delivery, not task reasoning.** Team operations insert a send message and create the ledger record (`src/server/team-operations.ts:604–645`). Stopped user-managed workers retain queued work; a never-started orchestrator-spawned worker is the special auto-start case (`src/server/routes-team.ts:31–35`, `src/server/routes-team.ts:145–160`). The queued dispatch is replayed on worker start (`src/server/team-operations.ts:496–597`). A claimed submitted record calls `agentRuntime.writeSendPrompt`, guarded again before writing (`src/server/team-operations.ts:670–685`).
4. **A prompt crosses the process boundary through PTY stdin.** The dispatcher builds the worker payload and writes it (`src/server/agent-stdin-dispatcher.ts:286–330`), using per-agent serialization (`src/server/agent-stdin-dispatcher.ts:135–144`) and startup-readiness gating (`src/server/agent-stdin-dispatcher.ts:164–204`). AgentManager launches the configured executable through the PTY wrapper and exposes process input (`src/server/agent-manager.ts:125–178`; `src/server/pty.ts:1–9`). Bootstrap prepends the packaged `team` command to PATH and supplies workspace/agent identity (`src/server/agent-run-bootstrap.ts:127–138`); the starter fills in the runtime port and token (`src/server/agent-run-starter.ts:112–143`).

## How progress and results return

- **Raw output:** PTY `onData` appends output and publishes it on the run's output bus (`src/server/agent-manager-support.ts:338–343`). The hub mirrors and enqueues it for attached viewers (`src/server/terminal-stream-hub.ts:145–158`). This independently exposes orchestrator and worker terminals; it is not the completion protocol.
- **Task-scoped progress:** `team message --dispatch D --to orchestrator --kind progress ...` uses `/api/team/message` with the agent identity (`src/cli/team.ts:1223–1250`). The route authenticates, validates the kind and calls `sendDispatchMessage` (`src/server/routes-team-messages.ts:34–71`). Message operations authorize the responsibility and recipient before inserting in a transaction (`src/server/dispatch-message-operations.ts:70–92`). The store writes the message but deliberately skips model-delivery outboxes for `progress` (`src/server/dispatch-message-store.ts:164–200`); required inbound acknowledgement sequences exclude progress (`src/server/dispatch-ledger-store.ts:347–356`). The Action Center includes recent dispatch messages (`src/server/action-center-summary.ts:189–212`), and `team messages` provides authenticated responsibility-scoped reads (`src/server/routes-team-messages.ts:73–91`). Silent progress does not awaken the orchestrator model or settle the task.
- **Legacy injected status:** `team status` POSTs text and optional artifact strings (`src/cli/team.ts:1538–1554`). Its route authenticates and requires worker permission (`src/server/routes-team.ts:449–474`). `statusTask` logs the update and invokes the status-prompt writer, without settling a dispatch (`src/server/team-operations.ts:916–977`). That writer targets the orchestrator's stdin (`src/server/agent-stdin-dispatcher.ts:276–284`). Forwarding is asynchronous and does not use the durable report outbox; a logged status need not have reached an unavailable orchestrator.
- **Result:** `team report` POSTs result text, optional dispatch ID, seen sequence and artifacts (`src/cli/team.ts:1557–1574`); the route authenticates it and sets `requireActiveRun: true` (`src/server/routes-team.ts:397–443`). Team operations find the worker's matching open dispatch, prepare the return payload and atomically insert the report, enqueue its outbox payload and settle the ledger (`src/server/team-operations.ts:978–1066`). The actual ledger write requires `seen_seq` to equal the latest required inbound non-progress message sequence; otherwise it returns conflict rather than closing another responsibility (`src/server/dispatch-ledger-store.ts:340–376`).
- **Durable return:** Store wiring supplies SQLite-backed ledger, message log and report outbox with a database transaction (`src/server/runtime-store-helpers.ts:414–438`); file-backed runtime initialization opens `runtime.sqlite`, with an in-memory branch when no data directory is configured (`src/server/runtime-database.ts:130–145`). Outbox draining calls `deliverSystemMessageToAgent` and marks delivery only after its write promise resolves (`src/server/team-operations.ts:298–323`; `src/server/agent-stdin-dispatcher.ts:393–399`). If the orchestrator is down the committed report stays queued (`src/server/team-operations.ts:1113–1132`); authenticated `team list` drains the caller's outbox after restart (`src/server/routes-workspaces.ts:151–167`). PTY write completion is not proof the agent understood the result.
- **Human-facing team view:** The Action Center polls its summary endpoint (`web/src/action-center/ActionCenterStrip.tsx:123–153`; `src/server/routes-action-center.ts:9–28`). Report notifications poll committed reported dispatches on a two-second timer (`web/src/notifications/useReportNotifications.ts:36–94`; `web/src/api.ts:2167–2183`). The overview's HTTP polling arrow represents these UI routes in the same runtime subsystem, not a call to `/api/team/send`.

## Task list is separate from dispatch

The browser task editor reads/writes task content; its PUT route only calls the task-file service (`src/server/routes-tasks.ts:40–80`). The canonical path is `.hive/tasks.md` (`src/server/tasks-file.ts:24–31`). The watcher reads changed content and emits updates (`src/server/tasks-file-watcher.ts:184–195`); the terminal server registers task updates and publishes through the tasks WebSocket server (`src/server/terminal-ws-server.ts:49–53`). The browser listens for `tasks-snapshot` and `tasks-updated` at `/ws/tasks/:workspaceId` (`web/src/tasks/useTasksFile.ts:98–110`). This is board synchronization, not an automatic task-list-to-worker scheduler. It is retained as a scope note rather than another main-path node.

## Boundaries, uncertainty and omissions

- The diagram separates browser session, local Node runtime and the two CLI child-process roles. Local CLI HTTP calls use per-agent credentials; browser sockets and UI HTTP reads use UI-session checks. Workspace membership is checked at the CLI boundary. These are implementation boundaries, not a claim that the CLI subprocesses are OS-sandboxed from workspace files.
- External agent reasoning, tool execution, whether a dispatch is obeyed, and the correctness of a reported result cannot be proven from Hive's transport code. Hive injects a prompt; it does not implement the external agent's execution loop.
- Artifact strings travel in the report; this path does not establish binary upload, verification, or guaranteed accessibility of those files.
- The local orchestrator/worker path is the focus. Optional remote/gateway transport, experimental workflows, memory enrichment, cancellation and session recovery internals are not expanded. Workflow-origin reports have a different in-process awaiter branch (`src/server/team-operations.ts:1076–1099`), not the orchestrator-PTY return shown here.
- The overview groups HTTP handlers, Team operations and stdin delivery into one runtime component, while preserving their distinct responsibilities in focused explanations and these references. SQLite access remains owned by the runtime, not the browser or CLI agents.
